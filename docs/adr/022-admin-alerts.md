# ADR-022. Тревоги админу в Telegram

Статус: принято, 04.10.2026. Пульт (ADR-021) показывает, что сломано, но сам никому не пишет —
это прямо записано в нём самом и в `docs/SYSTEM.md`: «смотреть надо самому». С сотней болельщиков
это перестаёт работать: о сбое в игровой день владелец узнаёт от болельщика в личке.

## Контекст

Всё, чтобы заметить поломку, уже есть. `admin.problems()` формулирует проблемы человеческим
языком («Живое: служба упала», «Бот не достучался до Telegram, проверь tg-tunnel», «Мини-апп не
собирался 2 ч»). Не хватает одного: кто-то должен это прочитать. Сейчас для этого нужно открыть
бота, нажать `/admin`, открыть пульт — то есть заранее знать, что что-то не так.

Два частных случая, которые нельзя терять:

- **Упал туннель в Telegram.** Бот жив, пульс пишет, но ни одно сообщение не уходит. Напоминание
  о матче не придёт сотне человек, и об этом не узнает никто.
- **Встала сборка Pages.** Мини-апп показывает вчерашний календарь и счёт, болельщик видит
  неправду.

Каналов для тревоги у нас ровно два: Telegram (есть у бота) и почта (ничего не настроено).
Telegram и так единственное место, где владелец читает систему.

## Решение

### 1. Кто считает и кто пишет

Разделение по тому, у кого какие данные:

- **Служба `api`** умеет собрать состояние: `systemctl show`, пульс бота, итоги заданий Actions,
  свежесть `league.json` и `live/`, диск. Она раз в две минуты строит тот же статус, что отдаёт
  пульту, и пишет список проблем в `status/alerts.json`: `{"at": …, "problems": [{level, key, text}]}`.
- **Бот** умеет писать в Telegram (у него туннель). Раз в минуту, тем же циклом, что пишет пульс,
  он читает `status/alerts.json` и разносит новое по `ADMIN_IDS`.

Почему не одна служба: у API нет выхода в Telegram (`api.telegram.org` с российского VPS закрыт,
туннель настроен только боту), а у бота нет ни `systemctl`, ни токена Actions. Файл между ними —
та же схема, по которой уже живут `status/bot.json` и `live/`.

### 2. У каждой проблемы есть ключ

`admin.problems()` возвращает теперь не только `level` и `text`, но и `key` — причину:
`service:bot`, `bot:telegram`, `build:pages`, `league`, `source:online.khl.ru`, `disk` и так далее.
Текст меняется каждую минуту («молчит 7 мин» → «молчит 8 мин»), ключ — нет. Без него любая
тревога повторялась бы с каждой проверкой.

### 3. Когда писать

- Новая причина — пишем сразу.
- Причина осталась — напоминаем не чаще раза в час, и только про `bad`. Про `warn` (красные
  тесты, служба перезапускалась, нет `PAGES_TOKEN`) пишем один раз: это «посмотреть», а не «горит».
- Причина исчезла — одно сообщение «починилось», и забываем её.
- Ночью (23:00–9:00 МСК, как и все рассылки бота) не пишем. Сломалось и само починилось ночью —
  утром не пишем ничего: шум без дела. Сломалось и осталось — утром придёт.
- Одна проверка — одно сообщение со всеми причинами, а не письмо на каждую. Кнопка «Открыть
  пульт» рядом: тревога говорит, что смотреть, пульт — подробности.
- `ADMIN_IDS` пуст — молчим: писать некому.

### 4. Пульт молчит — это тоже тревога

Если `status/alerts.json` старше десяти минут или его нет, бот пишет об этом сам: служба `api`
не работает или выложена старая версия. Так падение API не остаётся незамеченным из-за того, что
именно API должен был о нём сообщить.

## Чего не делаем

- **Не пишем из API напрямую в Telegram.** Это второй клиент Bot API, второй путь через туннель и
  второе место, где лежит токен.
- **Не чинимся сами.** Ни перезапуска служб, ни кнопок на пульте: пульт только показывает
  (ADR-021), тревога только говорит.
- **Не следим за собой извне.** Умер бот целиком — тревогу некому отправить, и это честное
  ограничение: пульс в `status/bot.json` есть, но смотреть на него изнутри того же процесса
  бессмысленно. Внешняя проверка (чужой uptime-монитор дёргает `/api/health`) — следующий шаг,
  и она же покрывает смерть всего сервера.
- **Не зовём по почте и не шлём SMS.** Пока хватает Telegram.

## Последствия

- Владелец узнаёт о сбое в минуту, когда он случился, а не от болельщика.
- `admin.problems()` становится источником правды не только для страницы, но и для рассылки:
  новая проверка автоматически становится тревогой, если у неё есть `key`.
- Служба `api` раз в две минуты делает работу, которую раньше делала только по открытию пульта
  (`systemctl show` и чтение файлов). Это дешёвая цена: один вызов `systemctl` и пара файлов.
- Файлов состояния становится больше: `status/alerts.json` (пишет api) и `alerted.json` (помнит
  бот, о чём уже сказал). Оба не в git и в бэкапе не нужны: потеря `alerted.json` стоит одной
  повторной тревоги, а `alerts.json` служба `api` перепишет через две минуты.
